Writing code is no longer the problem. Validating it is.

Since February 2026, AI has written every change to an existing 300,000-line application. Of 896 changes, 604 went through our review process, where AIs from different vendors review each other’s work. Here is what nine months of data show, and what they taught us.

Not a demo: maintenance

An agent that builds an app from scratch in ten minutes proves very little. Here, the code existed before us: 300,000 lines, imported into the repository at the end of January 2026, with their history, their dependencies and real users in production.

Every change is evolutionary maintenance: fix, extend, without breaking what works. Writing that code is still fast. The hard part is proving it breaks nothing.

Late 2025: AI writes, humans review

In late 2025, Claude Code turned the way we code upside down: an agent writes a whole change in a few dozen minutes. The first setup came naturally: AI writes, humans review.

It does not hold. A serious review takes hours, and code arrives faster than it can be read. That leaves two bad options: slow the AI down to human speed, or approve without really reviewing.

2026: AIs review each other

At the end of April 2026, we handed review over to AIs, in a process we call full-review. Several AIs review each change in turn. Every problem is fixed, then the review starts again, with another reviewer.

Nine months in four phases

What the numbers show

Since the end of the break-in period, on July 13:

376changes 2,542review passes 11,090problems found 97%of changes with at least one problem

It takes 5 passes per change, median. Only 11 of 376 shipped as the AI had written them.

In May, the second pass found nothing seven times out of ten. The code was not better: the review was less demanding. Tightened in June and July, it finds two to four times more problems from the first pass.

August is the peak: changes double in size, close to 1,000 lines median, and everything climbs with them. In October, the first pass still finds six problems, but the following ones almost none: the second pass is clean one time in two, against one time in ten in August.

Without a process, a change was merged in 1 h 20 min. During the break-in period, the delay explodes: close to 15 hours in June. Once the process is stable, it comes back to 4 to 6 hours. That is the price of validation, and this chart shows it plainly.

What one AI misses, another one sees

In 38% of changes, one AI judged the code clean, then an AI from another vendor found a problem in it. Same code, different eyes. That is why we use three vendors.

A real case

A change replaced an error with a fallback value whenever an external source sent corrupted data. The first review saw only a documentation detail. The second described it as an improvement, “safer”.

On the fourth pass, a model from another vendor followed that value to where it was used: it fed calculations of real amounts of money. The problem was rated critical, and the change was reverted.

Validating costs five to ten times more than writing

In the sessions where we could measure both phases, review takes five times longer than writing, median, and up to ten times. Writing takes a few dozen minutes, validating takes hours. It also burns far more tokens, with three reviewers per change.

Yet this is where AI made the most progress in 2026. It has become far better than humans at validating code, finding security flaws and fixing them before production. No human reviewer keeps the same focus from the first to the 2,542nd review.

What we learned

Every rule in the process comes from a real incident. We have logged 140 of them. Here are the seven lessons that changed the numbers most.

May 13A crashed review is not a clean review

A reviewer that crashes reports no problems. Counted as “clean”, it could ship a change nobody had read. Since then, a review that errors out is ignored, never counted.

May 22One problem found hides others

Fixing only the flagged line is not enough: the same flaw often sits elsewhere in the code. Before every fix, the AI searches the whole repository for the same pattern and fixes every occurrence, with a test for each.

June and JulyA single reviewer must never be able to close the loop

With two clean reviews in a row as the only exit rule, the loop could stop before the third reviewer had read the code. Now the last two clean reviews come from two different reviewers, and all three must have read the final version. That is what explains the median of 5 passes.

AugustCheck every suspicion before fixing

AIs flag many false problems. So every suspicion is checked in the code before it is fixed. Since September, 8,504 false alarms have been ruled out and passed on to the next reviewers so they do not raise them again.

June 4, then September 10Set the bar by what is at stake

A style detail in a test restarted the whole loop, just like a production bug. The bar is now high on running code and scripts, lower on tests and documentation. It is one of the changes behind the convergence in October.

AugustA rule that is not read is not applied

The process instructions had grown to 91,000 tokens, read in full on every pass. We split them: each step loads only what it needs, and each pass runs in a fresh agent, free of the noise of the previous ones.

ThroughoutThe process fixes itself

At the end of every review, the AI proposes improvements to its own rules. We review them and merge them in batches, several times a month. The October process is not the July one, and that is by design.

For developers
  • The reviewers: Claude (Anthropic), Codex (OpenAI) and Grok (xAI), in a fixed order.
  • Every fix follows TDD: a failing test first, the fix second. 2,979 fixes proven this way since July 13.
  • Keep changes small: in August, when their median size doubled, passes and problems climbed with it.
  • Every pass leaves a report line on the change: reviewer, problems, false alarms, fixes. All the numbers in this article come from those lines.

What is left for humans?

Giving the orders: deciding what to build, and to what standard. Writing and evolving the validation rules, like these seven lessons. And holding to one rule: delegate execution to AI, but not understanding. That will be the topic of the next articles.

One last lesson, to finish

These 300,000 lines are written mostly in Python. Alain, who runs the project, does not know Python: he can barely read it.

Yet 896 changes later, the application keeps evolving in production. The review does not hold thanks to a language expert. It holds only thanks to AI and the process around it. That may be the best proof that it works. The understanding he keeps is of the product and the rules, not of the syntax.

We set up this approach with dev teams, on their code and with their tools.
